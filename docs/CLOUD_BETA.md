# Android cloud beta

This branch adds the cloud foundation. It is not evidence of a deployed or device-accepted beta. The existing phone build and production website remain independent until activation below. No production-user migration is needed; joining from an older development build requires its explicit **Reset this phone for cloud beta** action. Do not silently clear the phone.

## What changes

The primary Google account signs into Nextbell through Firebase Authentication. Other Google accounts are separate data connections, verified with account-specific offline authorization codes. Refresh tokens are encrypted by KMS; the server OAuth client secret lives in Secret Manager. No Google refresh token or client secret belongs in Flutter configuration, SQLite, a Git commit, or application logs.

`packages/cloud` contains validated API contracts, Google clients, Firestore repositories and job orchestration. Next.js mounts versioned mobile APIs, a verified Google notification webhook and OIDC-authenticated worker routes. Flutter uses the same native alarm scheduler with a Drift cache/outbox. The iOS prototype keeps its existing direct-Google implementation; cloud sign-in is Android only in this beta. There is no web dashboard or browser sign-in yet.

The server discovers hidden/shared/subscribed calendars and keeps selections separate from provider metadata. Real events use a non-expanded incremental feed plus a bounded 7-day-past/90-day-future occurrence cache. A daily rebase advances the window. Pagination checkpoints survive worker retries; 410 sync-token responses rebuild the baseline. FreeBusy uses up to 50 calendars and 30-day windows, with per-source all-or-nothing publication. Calendar watches are renewed before expiry; tasks and busy blocks use periodic polling. Failures retain the last successful collection unless access has been lost.

Immutable collections publish atomically behind a user revision. Access epochs and account/selection guards prevent stale workers or older downloads from restoring inaccessible data. Preferences have optimistic versions and idempotency receipts. Conflicting edits remain visible; the user can keep their change or use the cloud setting. Task writes use a persisted ETag so retries cannot re-complete a task somebody subsequently edited in Google.

Every registered phone rings by default. A per-phone switch is applied locally immediately and queued offline; remote changes are pending until that phone reports the matching device version. Native scheduling coverage is reported separately from downloaded revisions. Snooze/Dismiss never synchronize between phones. Generic urgent-change pushes are quiet visible notices for qualifying moved/canceled meetings; routine sync pushes use normal priority. Push is a hint, not an alarm delivery mechanism.

## Verification and release gate

Local commands: `pnpm check:cloud`, `pnpm test:cloud`, `pnpm test:cloud:emulator` (Java 21+ on PATH), `pnpm check:web`, `pnpm build`, `pnpm test:web`, and `pnpm check:mobile`. Android Gradle needs Java 17; the Firebase emulator needs Java 21 or newer. The emulator project is `demo-nextbell`, with loopback-only ports 18088 and 19099, and never contacts the live database.

Before calling this beta ready, record a **48-hour soak** with the actual deployed revision, device build, queue latency, watch renewals, foreground/background refresh, outage recovery and billed usage. One-phone tests do not prove cross-device behavior. Use a second physical phone or a Play-enabled emulator for independent identity, switches, revision/coverage status and simultaneous-setting conflicts. Keep test event names generic, private and without guests or conference links.

- Sign in, kill/restart the process, lock the phone and verify restored identity and alarm scheduling.
- Connect the personal and work accounts; verify hidden/shared/private/free-busy calendars and task authorization remain independent.
- Move/cancel a meeting with an alarm in the next hour. Verify the quiet generic notice, then downloaded revision and actual alarm replacement. Confirm routine changes do not produce high-priority notices.
- Revoke a calendar permission, downgrade to busy-only, turn it off/on, split/merge busy blocks, expire an OAuth token and restore access. Inaccessible details and incompatible alarms must disappear.
- Edit defaults offline on two phones; resolve conflicts; disable this phone offline; remotely disable another phone and confirm it remains visibly pending until applied.
- Complete a task offline, reconnect, simulate response loss, then reopen the task in Google. A replay must not silently overwrite the reopened task.
- Confirm task alarms retain their chosen instant across Google date edits, DST and travel; local handled reminders are not recreated by repeated downloads.
- Delete a source account and the entire Nextbell account while one device is offline; verify cancellation, deletion, denied late writes and eventual cache cleanup. An unreachable phone may ring old alarms until it reconnects or is cleared locally.
- Test locked screen, reboot, offline alarms, battery restrictions, revoked permissions, capacity and Android force-stop. Existing direct-Google device results do **not** establish cloud-beta results.

The local Xcode installation is incomplete; iOS cloud is deferred, and an unsigned iOS build/native test run must still pass on a configured CI Mac. Keep the existing iOS CI checks.

## Operations, retention and rollback

Task dispatch is capped at one per second with two concurrent workers, retry backoff 15–600 seconds and 20 attempts / one hour. Per-account leases serialize jobs; source failures back off to at most hourly polling. Poll scheduling checks every five minutes but healthy accounts are due every 15 minutes. These are private-beta limits, not a promise of low latency at public scale. Watch registration is best effort and periodic refresh remains the fallback.

Monitor safe `nextbell_request_failed` log counters, HTTP 5xx, task oldest-age/retries, `syncHealth.lastError`, device applied/scheduled revision differences and earliest uncovered reminders. Do not log bearer tokens, codes, Google responses, event titles or URL bodies. Superseded versions/staging pages are explicitly deleted after 24 hours; Firestore TTL alone does not remove nested collections. Job/dispatch receipts expire after seven days, mutation/task receipts after 30. Backups expire within seven days; minimal deletion markers remain to reject late traffic. Before restoring a backup, preserve and reapply all deletion markers and run deletions before enabling API access.

Pause the task queue and both Scheduler jobs, set `NEXTBELL_SYNC_PAUSED=true`, and redeploy the last validated **beta** version to stop automated refresh. Inspect unapplied device revisions; already scheduled native alarms remain on phones. The kill switch must not prevent account deletion. For a complete beta shutdown, revoke server Google authorizations and clear device registrations only after notifying testers through an explicitly authorized channel. Never redirect cloud clients to an incompatible device-only server or delete production data as a rollback.

Budget alerts are notifications, not spending caps. Inspect Firestore operations/storage/PITR, KMS operations, Tasks, Scheduler and Vercel usage after the soak; count shared Google billing free tiers accurately. Vercel charges and tax may be separate from the Google budget. Confirm recurring cost against the $25 target before widening access.
